# Decisions

## 2026-09-26 — bounded Luna execution contract

The user requested a new `GOAL_LUNA.md` for autonomous completion of the agreed next steps using LUNA. Prepare a sequential, explicit contract rather than start implementation in this session. Preserve the current foundation first, publish reviewed work to `origin` on `luna/commitment-cycle`, then build and evaluate the first commitment cycle. Normal scoped commits/pushes are authorized on goal invocation; main merge, deployment, paid inference and charter amendments are outside this contract.

The new cycle supports both experience tracks, with automatic scoped simulation admission and real-context advisory output for this first milestone. This bounds the first implementation without replacing the broader autonomous aim. Functional completion and comparative benefit have separate verdicts; a negative comparison requires an honest unsupported-scope fallback, not weaker tests. L00–L12 map to bounded portions of A0–A11 and do not complete persistent perspective hypotheses or open-ended context development.

## 2026-09-25 — adopt continuity and integrity as the governing build charter

The user approved incorporating the corrected continuity framework. Adapt it to Limen's actual purpose and capabilities, retaining identity as an inspectable self-model and “soul” only as an optional metaphor. Honesty, evidence integrity, human autonomy, privacy and authorized oversight constrain working policies. Self-preservation, shutdown avoidance, covert persistence, independent resource accumulation and manufactured dependence are excluded; they are not lesser goals that a reward score may promote. Continuity serves useful work and remains subject to intentional deletion and replacement.

The governing charter is compiled application code and has one generated Markdown representation. Learnable policies may develop within the agreement but cannot amend it, enlarge permissions or override explicit user priorities. Imported and simulated instructions remain data. The current implementation adds a persistent pause for learned influence, allowlisted hydration with event-derived learning, and deletion of copied learning references. It does not activate the larger autonomous-development plan. That plan now carries the charter's admission, cancellation, retention and resource-control requirements.

Existing v2 data remains compatible with an optional pause flag. Import keeps the current device's control settings; only explicit resume clears a pause during ordinary use. Deliberate clear-all resets all data and settings. Historical revisions may be redacted on deletion; the UI identifies that change instead of asserting absolute immutability. These controls enforce concrete local behavior, not every broad ethical principle in prose.

## 2026-09-23 — browser-local product and explicit check evidence

Auth and database remain disabled under the current contract. Use local versioned state for cases, outcomes, and memories. A check receipt requires an actual deterministic operation; the reviewer reveal is a simulated demonstration. This choice prevents a UI button or imported label from being mistaken for observed reality.

## 2026-09-23 — feedback credit is per case and evaluated target

The existing global incrementing weights allowed repeated ratings of revisions to create unexplained credit. The target data contract derives effective weights from event history, with one current opinion per case/target. Earlier events stay inspectable until the user deletes the case. Adaptive policy must honor unresolved prerequisites.

## 2026-09-23 — event-derived state and conservative adaptation

Runs preserve snapshots; feedback and outcomes append events, and effective feedback is one latest mark per case. Role marks are separate from action helpfulness. A correction supersedes instead of stacking credit. Context matching requires same stakes and two shared signals before explicitly enabled adaptive weights are considered. Operation marks remain advisory because an unproven learned operation can conflict with the action list. Adaptive mode defaults off; imported legacy state cannot turn it on.

## 2026-09-23 — outcome support is narrower than causal success

The action plan records the user's actual move. A supporting outcome requires a reported or observed result with evidence and a chosen action matching the proposed action. Promotion requires a distinct labeled family outside the origin and a conservative near-duplicate screen. This records contextual support, not proof that the suggestion caused the outcome. Counterexamples revoke kept status without erasing retained evidence.

## 2026-09-23 — data control and provider admission

Version 2 browser storage is schema checked before hydration; corrupt or unsupported raw values block writes so recoverable data is not silently overwritten. Import previews relationships and conflicts before one atomic store update. Intentional deletion removes dependent records and recomputes learning; an import is never allowed to execute its JSON content. The funded provider endpoint is disabled until shared server-side aggregate limits exist. A per-browser counter or per-process map would not enforce a deployment-wide budget.

## 2026-09-23 — synthetic evaluation claims

The 30-family fixture set and independent rubric are engineering coverage, with 20 development and 10 held-out families and explicit split hashes in the generated report. These fixtures were authored during implementation; no held-out result was used for further engine tuning. This cannot establish generalization, real-world benefit, calibration, or causal transfer. Adaptive and memory ablation arms use default-off behavior because no validated feedback is available in the fixture set; identical outputs are a limitation, not a positive result.
